# 신규 기능 안내 초안 (2026-09-26)

> 이 문서는 도움말(HELP_GUIDE.md)에 추가할 내용을 위한 원본 초안입니다. GPT 등으로 다듬어 최종 문서에 반영하세요.
> 아래 3개 기능은 모두 오늘 하루 동안 순차적으로 개발/검증되었습니다.

## 1. 로그인 알림 팝업

### 무엇이 바뀌었나

로그인 직후, 확인이 필요한 항목이 있을 때만 팝업으로 안내합니다. 해당 사항이 없으면 아무것도 뜨지 않습니다.

### 일반 사용자에게 보이는 내용

- 임시저장한 채 등록을 완료하지 않은 Issue 건수 (예: "임시저장된 Issue가 2건 있습니다. 등록을 완료해주세요.")
- 내가 조치하거나 확인해야 할 Issue 건수 (내가 조치 중 + 확인대기 합산)

각 항목을 클릭하면 해당하는 MY 화면 탭으로 이동합니다.

### Quality Admin에게 보이는 내용

- 담당자가 근무일(주말 제외) 기준 2일 이상 지정되지 않은 Open 상태 Issue 건수
- 클릭하면 Kanban의 미배정 필터로 이동

### 공지사항

- Quality Admin이 설정에서 공지 제목/내용을 등록하고 "표시" 여부를 켜면, 모든 사용자의 로그인 팝업 최상단에 공지가 함께 표시됩니다.
- 공지 내용이 새로 바뀌면, 사용자가 예전에 "오늘 하루 보지 않기"를 눌렀어도 그날 다시 표시됩니다(변경된 공지는 다시 보게 하기 위함).

### "오늘 하루 보지 않기"

- 팝업 하단 체크박스를 선택하고 닫으면, 그날은 같은 팝업이 다시 뜨지 않습니다(브라우저 기준).
- 같은 브라우저 탭에서 새로고침해도 이미 봤다면 다시 뜨지 않습니다.

### 관리자 설정 (설정 > 운영설정)

- **로그인 알림 팝업 사용 여부**: 끄면 임시저장/조치대상/미배정 건수 알림이 전부 표시되지 않습니다(공지사항과는 별개 스위치).
- **공지사항**: 제목, 내용, 표시 여부(체크박스)를 관리자가 직접 입력합니다.

### 알아두면 좋은 점

- 팝업은 사용자마다, 그리고 로그인할 때마다 서버에 최신 건수를 조회해서 뜨는 것이라 실시간 상태를 반영합니다.
- 조치 대상 판단 기준: "내가 조치 중"은 내가 담당자로 지정된 진행 중 Issue, "확인대기"는 내가 등록했고 조치가 완료되어 검증을 기다리는 Issue입니다.

## 2. 외부 시스템 연동 API

### 무엇이 바뀌었나

사내 다른 시스템(예: 모니터링 툴, 알람 시스템)이 이 결함관리 서비스에 자동으로 결함(Defect) 티켓을 생성하거나, 조회/댓글/첨부/배포 등록을 할 수 있는 API를 새로 열었습니다.

### 인증 방식

- 설정 > 외부 연동 화면에서 관리자가 API Key를 발급합니다.
- 외부 시스템은 요청 헤더에 `X-Api-Key: <발급된 키>`를 담아 호출합니다.
- 키가 없거나 틀리면 401 오류를 반환합니다.
- API Key는 발급 직후 한 번만 화면에 표시되며, 이후에는 앞뒤 일부만 보이는 마스킹된 형태로만 확인할 수 있습니다.
- 관리자는 언제든 키를 재발급(기존 키 즉시 폐기)하거나, 사용 스위치를 꺼서 API 전체를 즉시 차단할 수 있습니다.

### 사번(employeeId) 지정

- 모든 요청에는 `employeeId`를 포함해야 합니다. 이 값이 실제로 어떤 사용자로 처리되는지를 결정합니다(등록자, 댓글 작성자 등).
- 등록되지 않은 사번이면 404 오류가 반환됩니다.
- 내부 화면에서 로그인할 때 쓰는 사번과 동일한 값을 사용합니다.

### 제공 범위

| 기능 | 메서드/경로 | 설명 |
|---|---|---|
| 결함 생성 | `POST /api/external/v1/issues` | 결함(Defect) 티켓만 생성 가능(개선요청/문의는 지원하지 않음) |
| 조회 | `GET /api/external/v1/issues/:id` | 사번 전달은 query string(`?employeeId=...`) |
| 배포 등록 | `POST /api/external/v1/issues/:id/deployments` | 조치자 본인 또는 Quality Admin만 가능. 조치 완료(Done) 이후에만 등록 가능 |
| 댓글 | `POST /api/external/v1/issues/:id/comments` | 등록자/조치자/Admin만 가능 |
| 첨부 업로드 | `POST /api/external/v1/issues/:id/attachments` | multipart 요청, 사번은 query string으로 전달 |

### 지원하지 않는 것 (의도적 제한)

- 상태를 직접 바꾸는 기능(조치 시작/조치 완료/종료/취소 등)은 외부 API로 제공하지 않습니다. 상태 변경은 반드시 내부 화면(웹)에서만 이루어집니다.
- 개선요청/문의 티켓 생성은 지원하지 않습니다. 결함만 가능합니다.
- 이미 다른 사람에게 배정된 Issue를 강제로 가져오는 기능은 없습니다(기존 워크플로 정책과 동일하게, 조치자 인계는 현재 조치자 본인 또는 Admin만 가능).

### 운영 시 참고

- 이 API는 내부망 접근을 전제로 설계되었습니다.
- 감사 추적을 위해 API Key 발급/폐기 이력이 서버 로그에 남습니다.

## 3. Kanban 개선 — 드래그앤드롭 상태 변경 + 미리보기 패널

### 3-1. 드래그앤드롭으로 상태 변경

#### 무엇이 바뀌었나

Kanban 카드마다 우측 상단에 작은 손잡이(⋮⋮)가 생겼습니다. 이 손잡이를 다음 컬럼으로 끌어다 놓으면, 상세 화면에서 버튼을 눌러 하던 것과 동일한 상태 변경이 그 자리에서 일어납니다.

#### 동작 방식

- 카드마다 "지금 내가 할 수 있는 다음 작업"이 오직 1개로 정해지며, 그 작업의 목적지 컬럼으로만 이동할 수 있습니다. (예: 접수 상태 카드는 조치중 컬럼으로만 이동 가능)
- 허용되지 않는 컬럼에는 애초에 드롭할 수 없습니다.
- 드롭한다고 바로 카드가 옮겨지는 것이 아니라, 필요한 입력(처리 결과, 확인 내용 등)을 받는 창이 뜨고, 그 창에서 저장을 완료해야 실제로 카드가 이동합니다.
- 창을 취소하면 카드는 원래 자리에 그대로 남습니다.
- 미배정 상태의 카드는 손잡이가 뜨지 않습니다. 기존처럼 "내게 배정" 버튼으로만 배정받을 수 있습니다.
- 카드 본문을 클릭하는 동작과 손잡이를 드래그하는 동작은 서로 분리되어 있어 혼동되지 않습니다.

#### 상태별 이동 예시

| 현재 상태 | 손잡이로 이동 가능한 컬럼 | 실행되는 작업 |
|---|---|---|
| 접수(Open) | 조치중 | 조치 시작 |
| 조치중(In Progress) | 확인대기 | 조치 완료(처리 결과 입력) |
| 확인대기(Done), 등록자/Admin인 경우 | 완료 | 정상 확인 |
| 확인대기(Done), 조치자/Admin인 경우 | 완료 | 합의 종료(Close) |

> 완료(Closed) 상태에서 되돌리기(Re-open), 취소(Cancel), 관리자 강제 상태 변경은 드래그로 지원하지 않으며 기존처럼 상세 화면에서만 가능합니다. 실수 방지를 위한 의도적인 제한입니다.

### 3-2. 카드 클릭 시 미리보기 패널

#### 무엇이 바뀌었나

Kanban 카드를 클릭하면 화면이 상세 페이지로 전환되지 않고, 화면 오른쪽에서 미리보기 패널이 나타납니다. 보고 있던 Kanban 화면(필터, 스크롤 위치)은 그대로 유지됩니다.

#### 패널에 표시되는 내용

- Issue ID, 유형/Priority/상태 배지, 제목
- 등록자, 조치자, 환경, 최근 업데이트 시각
- 발생 현상(결함) 또는 개선 내용/문의 내용 요약
- 다음 작업 버튼 1개(상세 화면과 동일한 기준으로 결정됨)

#### 패널 닫기

다음 세 가지 방법 중 어느 것으로든 닫을 수 있습니다.

- 패널 바깥(어두워진 배경 영역) 클릭
- 키보드 ESC
- 패널 우측 상단의 닫기(×) 버튼

#### 상세 화면으로 이동

패널 상단의 "상세 보기" 링크를 누르면 그때 비로소 전체 상세 화면(`#/issues/DEF-0001` 형태)으로 이동합니다. 댓글 작성, 첨부파일 관리, 이력(Timeline) 확인 등 전체 기능은 상세 화면에서 이용합니다.

## 참고: 이번 변경들의 공통 원칙

- 상태 변경 관련 로직(다음 작업 판단 기준)은 상세 화면과 Kanban이 동일한 코드를 공유하도록 만들어져, 두 화면에서 서로 다른 기준으로 동작하는 일이 없습니다.
- 서버의 기존 권한 규칙(등록자/조치자/Admin 구분)은 새 기능들에서도 그대로 적용됩니다. 새 기능이 기존 권한 체계를 우회하지 않습니다.
